# Changelog

## Unreleased

- Fix a saved answer or a failure that served after a key change: the cache key held the host and the request, but not the credential, and the Google, Clarity, PageSpeed, and Chrome UX Report keys go in headers. So after a user fixed a bad key, the 60 second failure window, or a Clarity answer saved until 00:00 UTC, still served the old result. Now each cache key, failure key, and shared call key holds a credential identity: the service account email for Search Console and GA4, and for an API key or a token a keyed hash with a random salt in the cache folder (`credential-salt`), so no key byte goes to disk. Entries of the old key format are not read. The Clarity and URL Inspection call ledgers stay of the project and the site, so a key change does not reset the count. A cache path with no identity fails a type check and a test.
- Fix `applied` of `get_seo_data` after a moved end date: it showed the asked `end_date` `2026-11-12`, but GA4 sent `today` and Search Console sent `2026-11-09`, so `applied` and `date_moved` disagreed. The tool text says that `applied` shows the values that a source used, so `applied.end_date` is now the `sent_end_date` of `date_moved`, in each range of a comparison too. `date_moved` keeps the asked date. A test of each source with an end date and a rule in the date model now fail when `applied` shows the asked end.
- Fix the `page_over_two_periods` task for a property that is new: it gave a GA4 comparison from 2026-09-11 for a property whose first day of data is 2026-10-08, so the step gave `delta` `null` and the agent had no next step. Discovery makes no call, so it cannot know that day. Now the `read` of each comparison step says that a range before the first day of data gives `delta` `null` and `first_data_day`, to ask the pair in `reason`, what to ask when that pair is too short or no pair fits, and to report the change as unknown when the server could not check the day. A test now runs each comparison step of each task against a new property and fails when its `read` does not say this.
- Fix 2 answers for the same Search Console days: `get_seo_data` gave `last_complete_day` from the API, and `query_api` `search_analytics` gave an estimate 2 days earlier, with 2 partial days and `incomplete` `true`. `query_api` read only its own reply, and the API gives `firstIncompleteDate` only for `dataState` `all` grouped by date. Now `query_api` reads the same saved coverage read as `get_seo_data` when its reply has no value, and uses the estimate only when that read gives none. Its saved answer serves only under the same API day. A source scan test now fails on a Search Console coverage that does not start from that read.
- Fix the `start_date` advice of the Clarity click tasks and the `query_api` tool text: it told an agent to reset the window after each site edit, so a site with a new blog post each day kept a window too short to show a click. Now the text says to set `start_date` only when the layout or the elements of the studied page changed, such as a moved button or a new form. New content on other pages does not reset the window. A source scan test now fails on text that resets the window on any site edit.
- Fix the `reason` of a date comparison with a range before the first day of data: it said only "Ask 2 ranges that start on or after" that day, so an agent had to find the dates, and could move only 1 start and compare different days. Now `reason` gives the exact pair: both starts move forward by the same days to `first_data_day`, both ends stay, and the parameter names say which range is main and which is comparison. A range that ends before that day, or is shorter than the move, gives no pair and says why. `delta` stays `null`, and no data changes.

- Fix a Clarity `get_seo_data` page answer at the row limit that showed `complete` `true`: 600 Traffic rows and 400 Dead Click Count rows passed, because the server checked each metric alone. The Data Export API gives at most 1,000 rows, and the docs do not say if the limit counts each metric or the whole answer. Now `get_seo_data` and `query_api` `live_insights` call 1 rule: when the rows of all metrics sum to 1,000 or more, `complete` is `false`, and `reason` names the limit and asks for a smaller `last_days`. A source scan test now fails on a Clarity path that compares rows with the limit itself.
- Fix a Clarity `live_insights` answer at the row limit that showed `more_rows` `no`: the Data Export API gives at most 1,000 rows with no paging, so 1,000 rows looked like all rows. When the rows of all metrics sum to 1,000 or more, `more_rows` is now `possible`, and `reason` names the limit and says how to read fewer rows. A source scan test now fails on a Clarity answer with rows and a fixed `more_rows` `no`.
- Explain the Search Console `position` in the `get_seo_data` and `query_api` tool text: an agent read a lower position, or a position `delta`, as good or bad. `position` is the average highest place of the link across all queries with impressions, so it moves when new queries appear. The text tells the agent to judge a change by clicks first, then by the click rate and impressions of the same rows.
- Fix a Clarity `dashboard_query` answer cut to a top list that showed `more_rows` `no`: 10 rows of "the top 10 pages by dead clicks" looked like all pages. When `answered_question` names a top N list and the answer has N rows, `more_rows` is now `possible`, and `reason` says that pages below the top N can have counts too, and how to read 1 page.
- Fix a `delta` of a date comparison that compared a range with no collected data: a GA4 property that started to collect inside the comparison range gave `delta` `{"sessions": 19}` with status `ok`, so an agent could report 7 times more traffic. Now a range of a date comparison with no row on its first day reads the first day of data of the property once (GA4 and Search Console), and `delta` is `null` when a range starts before that day. `first_data_day` names the day, and `reason` asks for ranges that start on or after it. A real 0 day after that day keeps the delta. No range moves.
- Explain a `search_queries` result whose rows sum to less than `totals`: it showed 0 clicks in each row with 17 clicks in `totals`, and no reason. Now `reason` gives the clicks and impressions of the rows past the first 25 and how to get them, and the clicks and impressions of the anonymized queries that Google leaves out of the rows.
- Fix a Clarity click task answer that was too large for the tool output of an agent: 50 recordings over 90 days made 68,321 characters. The click tasks now look back 28 days, inside the 30 days that Clarity keeps recordings, and ask for the 20 newest sessions. `recordings` asks for 20 by default, not 100. Each row keeps only `timestamp`, `link`, and each page `url` (with no query, so no `fbclid`) with its events, and an answer stops at about 40,000 characters of rows.
- Add `start_date` to `query_api` with `task`: each step of the task starts on that day, such as the day of a new design of the studied page.
- Fix an HTTP 200 answer of `{}` from the Search Console `sitemap` method of `query_api`: it showed status `ok` with 1 empty row. A sitemap that does not exist gives HTTP 404, and a real record holds `path`, so `{}` is now a wrong shape: status `error`, not saved, and the same request does not go out for 60 seconds.
- Fix an HTTP 200 answer of `{}` from a Search Console report or GA4 `metadata`: it showed status `ok` with 0 rows. Now it is a wrong shape: status `error`, not saved, and the same request does not go out for 60 seconds. `{}` of the Search Console sitemap list stays `ok`, because Google leaves out an empty list.
- Fix a false drop of the GA4 `engagementRate` in a range with a complete day and no sessions: `totals` showed 0, so `delta` showed a drop of the rate. With 0 sessions the rate is 0/0, so `engagementRate` and its `delta` are now `null`. The counts stay 0, and their `delta` shows the drop. In each `delta`, a metric that is `null` on 1 side is now `null`, also for a Clarity page that is not found.
- Enforce the 0 count rule of the Clarity click tasks in the server: after a saved dashboard count of 0 for the same click and days, `recordings` gives status `skipped`, sends nothing, and spends no call.
- Fix a GA4 drop to 0 traffic that showed no 0: a range with a complete day and no sessions gave `totals` `{}`, so `delta` showed no drop. Now `totals` holds 0 for each metric. A range of only partial days with no row has `totals` and `delta` `null`, and `reason` says that the total is unknown, the same as Search Console.
- Fix a saved Search Console report after Google moves `firstIncompleteDate`: it showed a day as complete with the partial rows of that day. The report now goes out again.
- Add a time frame, 1 page, 1 query, and a comparison of 2 periods or 2 pages to `get_seo_data`.
